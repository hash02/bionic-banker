# Public Proof Contract

Bionic Banker packages real work into public-safe proof surfaces. Every page should help a cold reviewer understand:

1. What system exists.
2. What evidence supports it.
3. What the system is allowed to do.
4. What remains human-gated or outside scope.
5. What a recruiter, collaborator, technical reviewer, or investor should inspect next.

## Preferred framing

Use concrete proof language:

- risk judgment
- evidence preservation
- audit trail
- reviewer-ready packet
- human approval boundary
- visible limitation
- public-safe artifact
- field map
- mission / stop / next move when using the game-board layer

Avoid weak or unsafe framing:

- generic AI-powered claims
- production-ready claims without dedicated production evidence
- autonomous profit language
- live trading authority
- legal/compliance authority overclaims
- raw JSON as the primary reader destination
- internal system lore that a cold reader cannot decode

## Public-safe data rule

Public pages and JSON can summarize status, checks, counts, provenance, and boundaries. They must not include secrets, tokens, API keys, private prompts, seed phrases, private keys, internal IPs, local filesystem paths, raw logs, or full wallet addresses unless Hash explicitly approves a public wallet page.

## Evidence structure pattern

For each public system card or proof page, prefer:

- Label: what kind of artifact this is.
- Claim: one bounded thing the system demonstrates.
- Evidence: links, checks, artifacts, counts, source pages.
- Boundary: what the system cannot or must not do.
- Reviewer question: what this proves about Hash's judgment.

## Authority boundary text

Keep boundaries explicit and boring. Good examples:

- Human approval required before external action.
- No live trading, wallet movement, or fund transfer authority.
- No SAR filing, KYC approval, enforcement, or final compliance decision.
- Public proof is not production authority.
