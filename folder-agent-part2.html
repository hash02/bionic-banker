The Technical Blueprint — How to Actually Build a Folder Agent

Part 2: Scripts aren't agents. Here's what's actually missing — and the code to fix it.

March 2026 · 12 min read

This is Part 2. Read Part 1: The Philosophy first if you haven't.

The Honest Confession

After I published Part 1, I asked myself a question that I should've asked before writing a single word: is this actually an agent?

And the honest answer is — no. Not yet.

What I built in Part 1 is a really well-organized set of scripts with good file hygiene. The outcome tracker detects patterns. The rule proposer generates proposals. The event router logs everything. It looks like agency. It feels like agency. But here's the test that breaks the illusion:

If I close my laptop and walk away for a week, does anything happen?

No. Nothing runs unless I open a chat window and trigger it. That's not an agent — that's a toolkit. A really good toolkit, but a toolkit. The difference between a toolkit and an agent is the same difference between a car with no ignition and a car that drives itself. The engine is there. The transmission works. But nothing moves until someone push-starts it.

So this article is about building the ignition.

The Four Things That Were Missing

I spent a while looking at my system and asking: what would it take to make this actually run without me? Not philosophically — architecturally. What's the minimum set of components that turns "scripts I run" into "a system that runs itself"?

Four things. That's it.

1. A heartbeat. Something that keeps running even when I'm not looking. A persistent process — a daemon, a cron job, a scheduled task. The simplest version: a Python script that wakes up every 6 hours and checks the folder. If nothing needs doing, it goes back to sleep. If something does — it acts. This is the ignition switch. Without it, the car doesn't start.

2. A brain that calls itself. Right now, Claude exists inside a chat window that I manually open. For the system to work independently, it needs a script that calls the Claude API directly — no chat UI, no human starting a session. Just code that says: "here's the current state of my folder, what should I do?" and gets back a structured response.

3. A communication channel. If the agent is running on its own, I need a way to hear from it without opening the app. Telegram bot, email, Discord — something that can tap my shoulder and say "hey, I noticed something." And I need a way to respond. "Approved." "Hold off." "Run the audit."

4. A safety boundary. This is the one most people skip and then regret. If an AI system is running autonomously, it needs a whitelist of what it's allowed to do. Not "guidelines" — a hard-coded list. Can run audits? Yes. Can delete files? Never. Can push to git? Only with explicit approval. The safety boundary is what makes the difference between "useful autonomous system" and "thing that broke my production website at 3am."

The Architecture — Five Files

Here's what surprised me: the entire agent architecture is five Python files. Total. I was expecting it to be more complicated — frameworks, orchestration layers, vector databases, whatever the AI Twitter hype cycle is selling this week. But no. Five files.

heartbeat.py — The loop. Wakes up on a schedule, runs one cycle (read state → call brain → execute actions → log → notify), then sleeps. Can run as a single check or as a daemon that runs forever. Has a --dry-run mode that shows what it would do without actually doing anything. This is important — you always want to be able to test the brain's decisions without consequences.

state.py — The eyes. Reads TASKS.md, INBOX.md, OUTBOX.md, proposals.md, outcomes.json, and the latest audit and health reports. Compresses everything into about 2000 tokens of context. The brain doesn't need to see every file — it needs a summary good enough to make decisions. Think of it like a morning briefing: what's active, what's broken, what's pending.

brain.py — The decision maker. Takes the compressed state, builds a constrained prompt, and calls the Claude API. The key word is constrained. The system prompt tells Claude: here are the only actions you're allowed to return. Anything else gets blocked. The response comes back as JSON — a list of actions with reasons. No prose, no conversation — just decisions.

comm.py — The voice. Sends messages through whatever channel is configured. Tries Telegram first (real-time, mobile), falls back to email, and always writes to a local file as backup. The agent should never be silent — if it can't reach you, it logs the message so you see it next time you check.

config.py — The settings. API keys, workspace path, model selection, schedule interval, safety limits. Reads from environment variables and a .env file. One file to change when you move the agent from your laptop to a server.

That's it. Five files. The entire distance from "scripts I manually run" to "system that runs itself" is about 400 lines of Python and a cron job.

The Brain's Constraint System

This is worth going deeper on because it's where most autonomous AI systems go wrong.

The brain doesn't get an open-ended prompt like "do whatever you think is best." That's how you get an AI that decides to reorganize your entire file system at 3am because it thought it would be "more efficient." Instead, it gets a whitelist:

SAFE_ACTIONS = {
    "run_audit",           # content audit script
    "run_health",          # health check script
    "run_outcome_tracker", # analyze patterns
    "run_rule_proposer",   # generate proposals
    "write_proposal",      # write a new proposal
    "notify",              # send message to me
    "noop",                # do nothing
}

Seven actions. That's the entire action space. If the brain returns anything not on this list, it gets blocked and logged. The brain can reason about anything — but it can only do seven things. This is the principle: give the AI unlimited intelligence with limited authority.

And notice what's NOT on the list: delete files, modify config, push to git, create accounts, send emails to people who aren't me. The absence is the safety.

There's another constraint that matters: the brain defaults to "noop." If it's not sure what to do, it does nothing and sends me a notification. This is the opposite of how most AI agents are designed — they default to action because that feels more impressive in a demo. But in production, the best action is usually no action. Most of the time, the folder is fine. The agent's job is to watch, not to perform.

What It Actually Costs

One thing nobody talks about with AI agents: the API bill. If your agent runs a loop that calls Claude every 30 seconds, you're burning money on context that hasn't changed. So I built cost control in from the start.

The default model is Claude Haiku — the smallest, fastest, cheapest. At roughly $0.001 per cycle, running 4 times a day costs about $0.12/month. A dollar twenty a year to have your folder check itself. If the brain needs to make a complex decision, it can escalate to Sonnet (~$0.01/cycle), but that's the exception, not the rule.

There's also a max daily call limit (default: 10) as a circuit breaker. If something goes wrong and the loop starts running too fast, it caps at 10 calls and stops. Paranoia-driven engineering — but the kind that lets you sleep at night.

The Linux Question

Okay so I need to talk about this because it's a fork in the road that actually matters.

Right now my system runs on Windows. It works fine for development — I build the scripts, test them, run them manually or through Claude Code. But for a true always-on agent, Windows is fighting the grain. Task Scheduler is clunky. Services are over-engineered for something this simple. And if my laptop goes to sleep, the agent goes to sleep.

The real move is a $5/month Linux VPS. DigitalOcean, Hetzner, whatever. Ubuntu, a cron job, and the five files I just described. The agent runs 24/7 regardless of whether my laptop is open. I can talk to it from my phone via Telegram while I'm at work. It checks the folder (synced via OneDrive or git), decides what needs doing, and either acts or notifies me.

The architecture doesn't change at all — you literally just change one line in config.py (the workspace path) and set up a cron job instead of running the daemon manually. That's the benefit of building it as plain Python with no framework dependencies. It runs anywhere Python runs.

From Chat Transcripts to Content

Here's where it gets interesting — and where the agent starts paying for itself.

Every conversation I have with Claude generates insights, decisions, and technical details that could become blog posts. Right now, the flow is manual: I have a conversation, realize there's a blog in it, then spend time extracting and rewriting. But the agent could automate the extraction.

The concept: I drop a chat transcript into a drafts/incoming/ folder. The agent's heartbeat detects the new file. It calls Claude with the prompt "extract the key insights from this conversation and draft a blog post using HASH's voice." The draft lands in drafts/ready/. I get a Telegram notification: "New draft ready for review." I read it, edit it, approve it. The agent publishes.

That's the content flywheel closing its own loop — conversations → drafts → review → publish → social → traffic → more conversations. Each piece feeds the next. And the agent manages the pipeline.

I haven't built this part yet. But the architecture supports it — it's just another action type in the whitelist and another prompt in the brain. The scaffolding is there.

What I'd Tell My Past Self

If I could go back to when I started this project and give myself one piece of advice, it would be: the agent isn't the AI. The agent is the loop.

I spent months building increasingly sophisticated scripts — audit systems, event routers, outcome trackers, rule proposers. All good, all necessary. But none of them are the agent. The agent is the thing that decides when to run them and what to do with the results. And that thing is embarrassingly simple — a while loop, an API call, and a sleep timer.

Every "AI agent framework" being sold right now is selling orchestration around this same loop. LangChain, CrewAI, AutoGen — strip away the abstractions and it's all the same: read state → call LLM → parse response → act → repeat. The framework adds convenience and cost. The loop adds agency.

You don't need the framework. You need the loop.

"An agent is just a loop that notices."

What's Still Missing (Honestly)

I want to end with what I haven't solved yet, because the internet has enough posts that pretend everything works perfectly.

The proof problem. RULE-001 — the first rule my system proposed — was detecting a pattern I designed the detector to find. The audit script was checking for empty heading tags. The outcome tracker was watching audit results. I built the detector AND the thing it detected. That's not the system being smart — that's me being thorough in the setup. Real proof of agency would be the system noticing something I didn't anticipate. That hasn't happened yet.

The memory problem. The compressed state works for short-term decisions, but the agent doesn't have true long-term memory. It can't say "last month when this happened, we did X and it worked." Every cycle starts fresh. There are ways to fix this (embedding-based retrieval, rolling summaries) but I haven't built them yet.

The multi-step problem. Right now each cycle is independent — read state, decide, act, done. But some problems need multi-step reasoning: "run the audit, check the results, then decide whether to run the proposer." The current architecture doesn't chain cycles together. Each heartbeat is stateless. Adding multi-step planning is the next evolution.

The trust problem. Even with all the safety boundaries, there's a philosophical question I can't engineer away: how much autonomy do you give a system that's smarter than your safety boundaries? Right now my whitelist has 7 actions. What happens when the agent correctly identifies that it needs an 8th action to fix a real problem? It can propose it — but what if I'm not around to approve? This is the alignment problem at the smallest possible scale, and I don't have a clean answer.

The Roadmap

Here's what I'm building next, in order of progressive complexity:

Phase 1 (this week): Deploy the heartbeat on Windows with Task Scheduler. Run it in dry-run mode for a few days. Watch what the brain decides. Tune the prompts until the decisions feel right.

Phase 2 (this month): Set up a Telegram bot. Get real-time notifications on my phone. Add the ability to approve proposals by replying to a Telegram message.

Phase 3 (next month): Move to a $5 Linux VPS. Run the agent 24/7. Add the content extraction pipeline — chat transcripts → drafts → review → publish.

Phase 4 (someday): Multi-step reasoning. Rolling memory. And maybe — maybe — expanding the whitelist to let the agent deploy content without my approval, once the trust is earned.

Each phase is a level-up. Each one compounds on the last. And each one teaches me something about what agency actually means — not the definition you read in an AI textbook, but the practical reality of building a system that works without you.

The folder was never the agent. The folder was the body. The scripts were the nervous system. The heartbeat is the pulse. And the brain — the thing that looks at the state of the world and decides what to do about it — that's the last piece.

Fifty lines of Python. A cron job. And a hard-coded list of things it's not allowed to do.

That's an agent.
