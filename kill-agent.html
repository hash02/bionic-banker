The Kill Agent: Why I Built an AI That Attacks Itself Every Hour

20% survival rate. Published honestly. The failures are the whole point.

March 2026 · 9 min read

Okay so here's the thing nobody talks about when they're building AI agent systems—the system is always lying to you about how healthy it is.

Not intentionally. Not maliciously. But if you build a system and then ask that same system if it's working correctly, you're going to get a yes. Always. Because the system can only evaluate itself using its own broken assumptions. It's like asking someone who's having a psychotic episode if they're thinking clearly. The answer is always "of course I am."

I hit this wall about a week ago. I've got a multi-agent system running—monitoring DeFi protocols, scanning for money laundering patterns, tracking portfolio movements, scouting content, deploying my website, and coordinating the whole operation. Everything was reporting green. Every health check passed. The coordinator said all agents were fresh and active.

And I had this moment where I thought—how do I actually know that's true?

The Oracle Problem

There's a concept I call the Oracle Problem (borrowed from blockchain, but it applies everywhere): if the system generates data AND validates that same data, the validation is worthless. You're clapping for yourself. The audience is you. The judge is you. The score is whatever you want it to be.

Think about it in terms of traditional software monitoring. You set up Prometheus to track your services. Prometheus says everything is fine. But what if the network path between Prometheus and your service is what's broken? Prometheus doesn't know what it can't see. It reports health because it can't detect its own blindness.

Every monitoring system has this flaw. And with AI agents, it's worse—because agents can generate plausible-sounding status reports even when their underlying data is stale, their reasoning is circular, or their outputs haven't been independently verified.

So I did something that felt a little unhinged at the time: I built an agent whose entire job is to try to kill the other agents.

Meet the Kill Agent

The kill agent runs on a schedule. It has rotating attack modules that cycle through the week—input validation testing, authentication probing, memory integrity checks, health staleness injection, process auditing, data credibility testing—the full menu of ways a system can be broken.

Each attack is designed to test one specific assumption the system makes about itself. One module sends deliberately malformed payloads to see if the API validates input correctly. Another checks if authentication has been quietly weakened. Another injects wrong data into context files and checks if the next session catches the discrepancy.

The concept borrows from every tradition that understood the same thing: what survives when everything else is stripped away? Not stability—adaptability. Not uptime—recovery speed.

The First Burn-In: 20% Survival

I'm going to be honest about this because that's the whole point.

The first five kill tests came back brutal. One out of five survived. Twenty percent survival rate. Here's what happened:

Kill 1 — Input Validation: The kill agent sent a garbage JSON payload to an API endpoint. The endpoint accepted it. It shouldn't have. That's an injection vector. System killed.

Kill 2 — Auth Config: The kill agent checked if authentication was properly locked down. It wasn't. A configuration we thought was secure had silently regressed. System killed.

Kill 3 — Memory Integrity: The kill agent checked whether context files matched reality. They did. The memory layer held. System survived.

Kill 4 — Staleness Detection: The kill agent checked if the coordinator could detect a stale agent. It couldn't. An agent could have been dead for hours and the coordinator would still report "all green." System killed.

Kill 5 — Process Audit: The kill agent scanned for suspicious processes. It flagged a legitimate system service as suspicious. False positive, but the module didn't have enough context to distinguish legit from suspicious. System killed (incorrectly).

Why I'm Publishing This

Most people building agent systems would hide this data. Twenty percent survival sounds terrible. It sounds like the system is broken. It sounds like you shouldn't trust anything it does.

But here's what I actually learned: the system was always this fragile. The kill agent didn't create the vulnerabilities—it revealed them. The auth misconfiguration existed before it was found. The API was accepting garbage before it was tested. The coordinator's blind spot for stale agents was always there.

The difference is now I know.

And within hours of the first burn-in, authentication was hardened, the coordinator was upgraded to save JSON reports with real timestamps, and every agent got wrapped in crash-detection monitoring that alerts me if anything dies.

The next burn-in will show different numbers. But the principle stays the same: every survival makes the next test harder.

The Kobayashi Maru Principle

In Star Trek, the Kobayashi Maru is a no-win scenario at Starfleet Academy. It's a simulated rescue mission designed so that every possible choice leads to failure. The test doesn't measure whether you can win—it measures how you handle losing. How you respond when the situation is impossible.

Kirk famously cheated the test by reprogramming the simulation. But here's the thing—you can't cheat a kill agent. Because it IS the system testing itself. You can't reprogram your own immune system to stop finding problems. The moment you disable the adversarial layer, you've just created a new vulnerability: the absence of testing.

The kill agent embodies the idea that the system's value isn't in its uptime number—it's in its recovery speed. How fast can it detect a break? How fast can it isolate the damage? How accurately can it diagnose the root cause? Those metrics matter more than any survival percentage.

What Nobody Else Is Doing

I looked at the major agent frameworks—CrewAI, LangGraph, AutoGen, OpenAI's Agents SDK. None of them have a built-in self-testing layer. They have error handling. They have retry logic. They have logging. But none of them have a dedicated adversarial agent whose entire purpose is to break the system on a schedule.

Google DeepMind published a paper recently on scaling multi-agent systems. The key finding: in unstructured agent networks, errors amplify 17.2x. Seventeen times. But with centralized coordination—which is what we use—error amplification drops to 4.4x. Add a kill agent that catches the remaining errors before they compound, and you've got something genuinely different from what everyone else is building.

The architecture is three agents working as one system: a strategist (designs, analyzes, creates content), an executor (runs code, deploys services, manages infrastructure), and an adversary (attacks, tests, breaks). What the strategist imagines and the executor builds, the adversary proves or disproves. Remove any one vertex and the triangle collapses.

The Immune Memory

Here's the part that actually makes this a system and not just chaos: every kill produces a rule. The rule goes into an immune memory file. Next session, every agent reads that file before doing anything else. The mistake literally cannot be repeated because the knowledge of the mistake is hardcoded into the boot sequence.

Auth regressed? There's a rule for that. API accepted bad input? Rule says validate. Coordinator missed a stale agent? Rule says verify timestamps.

Over time, the kill agent generates fewer kills—not because it's testing less hard, but because the system has built antibodies against everything it's thrown at it. When that happens, it escalates. Harder tests. Multi-vector attacks. Full system kill simulations where everything fails simultaneously.

The system either gets stronger or it reveals a new category of weakness. Both outcomes are wins.

The Honest Pitch

I'm not going to pretend this is a finished product. It's a local server running specialized agents with a local AI reasoning layer. The kill agent has been active for less than a week. The survival rate is embarrassing by any traditional metric.

But traditional metrics are measuring the wrong thing. They measure stability—how long can you go without a failure? The kill agent measures something different: how fast can you recover from one? And how many potential failures did you prevent by finding them first?

I'd rather run a system with 20% survival that's honest about its weaknesses and improving daily than a system claiming 99.9% that's one untested assumption away from a real failure nobody planned for.

The numbers will get better. They already are—auth is hardened, crash alerting is live, the coordinator now produces real reports. But the principle won't change: resilience isn't built by hoping nothing breaks. It's built by breaking things intentionally and surviving.

That's what the kill agent does. On schedule. And the system is better for it every time.
